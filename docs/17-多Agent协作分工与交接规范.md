# 多 Agent 协作分工与交接规范

2026-09-16：用户提出并行协作。采用一个主控开发 Agent 加三个专业 Agent；本轮启动三个只读子任务审核分工，尚未启动下一批代码与资源生产。进度统一维护在 [工作排期表](14-工作排期表.md)。

## 1. 四个角色

| 角色 | 责任与决策范围 | 主要交付 | 不自行决定的事项 |
| --- | --- | --- | --- |
| 主控开发 Agent（当前任务） | 整体顺序、地图与确定性规则、接口、集成、缺陷修复分派、进度和 Git 同步 | 分区地图比较、规则实现、集成版本、排期与设计记录 | 不把技术通过当作真人认可；公开部署仍遵守授权要求 |
| 测试回归 Agent | 独立验收每个集成版本，规则边界、全流程与回归缺陷 | 回归清单、必要的自动测试、复现步骤与证据、通过／不通过／未测报告 | 不为让测试通过而改产品规则；不直接修业务代码 |
| 美术资源 Agent | low-poly 温暖微缩风格、资源参考、模型与效果制作、资源预算和来源 | 模型工厂或合规资产、状态预览、规格与来源清单 | 不改模拟判定；概念图不作为可用三维模型交付 |
| UI／UE Agent | 信息层级、交互状态、操作反馈、标题与结算、键盘和小屏可用性 | 界面方案、状态表、独立 UI 模块与样式、交互自检 | 不另行定义胜负、预算、设施效果或存档行为 |

主控同时承担核心规则开发，当前无需再加一个策划或规则 Agent。用户负责方向评估；真人试玩由实际参与者完成。四个角色不代表四份独立需求，各自执行同一套已确认规则。

## 2. 先划边界，再并行写代码

当前 `src/main.ts` 同时含界面、事件和流程，`src/view.ts` 同时含模型和渲染。直接让 UI、美术、主控同时编辑会冲突。下面的新目录是拟议边界，尚未创建；主控先做必要的最小抽离和接口定义，避免大规模重构。

| 文件／区域 | 唯一写入负责人 | 其他 Agent 的方式 |
| --- | --- | --- |
| `src/sim/model.ts`、地图配表 | 主控 | 提建议、反例与验收要求 |
| `src/main.ts`、`src/view.ts`、`src/audio.ts` | 主控 | 提交精确接入说明；未经移交不直接修改 |
| 拟建 `src/ui/`、`src/style.css` | UI／UE | 主控通过约定接口接入；交回前不同时写 |
| 拟建 `src/art/`、`public/assets/models/` | 美术 | 交模型与状态控制接口，由主控接入 view |
| `src/sim/*.test.ts`、拟建 `docs/qa/` | 测试 | 主控提出规则变更契约；测试独立写用例 |
| 拟建 `docs/ui/`、`docs/art/` | 对应专业 Agent | 文档中文命名，单文件明确负责人 |
| README、规则、排期、开发记录、决策和来源总表 | 主控 | 专业 Agent 提供待合并摘要，避免多人争写 |
| package 文件、构建配置、公共类型 | 主控 | 新依赖或接口变更先提出请求 |

文件所有权按任务批次移交。需要越界时暂停该文件写入，报告原因，由主控调整负责人。禁止为了避开冲突复制一份模拟逻辑到 UI 或渲染中。

接口约定：UI 读取主控提供的只读状态，通过操作事件请求变更；美术只根据状态表现，不能自行计算是否保护成功。现有固定步长模拟与渲染分离要求不变。新增阻断、负载等表现必须先明确实际数据来源，不能从动画猜测规则结果。

本轮三个专业 Agent 的只读审核补充：

- UI：现有 DOM ID 是事件绑定契约；预算、目标、时长应由规则数据传入，避免多处写死。存档统一由主控管理。
- 美术：优先程序化模型，遵守 docs15 的尺寸与面数预算；交付需含源码、实际视角预览、材质与三角面数量及来源。共享材质必须约定释放责任，避免与现有 view 的释放逻辑冲突。ART-07 界面资源由 UI 主责。
- 测试：旧地图“默认全损、完整西侧防线全保”是版本基线，不是永久产品需求；S2 改图后按新规则更新预期，不通过放宽断言掩盖缺陷。

## 4. 每轮交接与验收

主控派发任务必须包含：工作编号、基线提交、目标、可写文件、禁止修改区域、输入接口、交付物和验收口径。专业 Agent 返回：修改摘要、文件列表、自检结果、未解决问题、接入步骤；测试结果必须附对应版本。

统一状态：待开始 → 进行中 → 待集成 → 待回归 → 技术通过。存在阻碍则标记阻塞及依赖；需要真人判断的项目另标待试玩。专业 Agent 宣布完成不等于整体已验收。

回归分两层：

1. 每个集成批次检查必要规则测试与 `npm run build`（含类型检查），完成一遍核心流程；涉及功能的边界要定向回归。
2. 里程碑再做完整桌面流程、子路径构建、存档、键盘与响应式检查。真实手机、低端设备、听感和首次玩家判断分别记录，不能用桌面模拟替代。

阻断验收的例子：不能开始／重试、住宅与预算不守恒、同布局不同速度结果不一致、存档损坏、页面报错阻断流程。视觉间距等轻微问题记录后由主控排期，不与破坏核心流程的缺陷混为一类。

缺陷记录模板：版本｜工作编号｜环境｜前置布局｜操作步骤｜预期｜实际｜证据｜严重度｜修复负责人｜复测结果。

## 5. 协作环境与同步

当前子 Agent 共享工作目录，按文件所有权并行；子 Agent 不自行切分支、提交、拉取或推送。主控检查全部差异后统一提交同步。浏览器验收期间由测试 Agent 独占指定标签页和预览服务，其他 Agent 不重启服务、不覆盖存档、不操作同一页面；测试布局使用独立存储或先备份恢复。

验收优先使用独立预览端口，以隔离用户页面的 localStorage；构建产物也须冻结，不能让其他构建覆盖正在验收的目录。UI 如需浏览器自检，由主控安排窗口移交。

如果以后由用户在多设备独立运行 Agent，使用各自克隆或 worktree，并用 `codex/规则-*`、`codex/测试-*`、`codex/美术-*`、`codex/交互-*` 等分支隔离；基于同一提交分工，主控逐个合并后再次回归。分支隔离不免除接口协调。不得共享凭证或强推。

专业子任务是当前工作的协作单元，本轮不创建四个独立常驻任务或后台自动验收服务。后续每批由主控调度具体任务；没有实际执行就不把状态写成完成。并行收益取决于依赖与集成成本，原排期的 7–12 小时粗估不能简单除以四。
