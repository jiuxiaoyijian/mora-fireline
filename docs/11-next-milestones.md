# 火线街区：后续目标与优先级（待评估）

日期：2026-09-15。基线：`b297cb1`，可玩实现仍为 v0.1。

用户已明确继续《火线街区》，提升玩法体验和原型完成度。本文件是供用户评估的下一步计划；这里的版本号、数值、关卡和验收目标都是提案，尚未实现或证明达到。

## 1. 下一阶段想交付什么

目标体验：**玩家能在短时间内完成一次实验，理解至少一个损失原因，提出一个布局改动，并在下一次实验中看见可解释的差异。**

整体仍采用「建造 → 模拟 → 观察 → 调整 → 重试」，保留 3D 街区、防火带、消防设施、预算和确定性火灾。继续原方向，不开发此前比较的异常观察或立体断路塔。

建议的产品边界：

- 决策集中在建造阶段；模拟期间以观察、暂停和加速为主。
- 先让一张地图值得重复实验，再做 2–3 个配表驱动的挑战。
- 保留住宅布局调整的自由度。关卡约束要在地图上提前显示，不能靠隐藏规则强迫唯一解。
- 优先保护住宅；达标后的剩余预算作为优化目标，暂不加入复杂总分公式。
- 以桌面浏览器提交为主，窄屏保证可用；是否专项支持手机操作在桌面闭环验证后再决定。

## 2. 排序依据

本轮采用已有审核证据，不重新声称已做试玩：

1. 默认布局 19.6 秒全部烧毁，但 45 秒结算，存在 25.4 秒后续等待。
2. 默认住宅不变时，西侧六格防火带的 64 个子集中，63 个保住 0 栋，1 个保住 12 栋。
3. 完整防火带花 6 点满保护，两座消防站花 8 点；同一固定场景缺乏体现两类设施取舍的目标。
4. 事件列表能定位点燃时间与相邻热源，尚不能充分解释布局为什么失效。
5. 已有自动检查与浏览器 QA，没有外部首次玩家体验证据。

以上数据的范围和复现方法见 [选型审核](10-prototype-triage.md) 与 [原始结果](evidence/triage-v01.json)。

## 3. P0：下一轮必须先验证的玩法基础

P0 表示阻碍核心体验的事项。按下表顺序交付，测试与记录随每项进行。

| ID | 工作目标 | 具体工作 | 验收依据 | 新增成本 |
| --- | --- | --- | --- | --- |
| P0-1 | 缩短无信息等待 | 加入「直接查看结果」；全部住宅已失守时允许明确提前结算；保留可读的首次传播节奏 | 跳至结果与完整模拟结果一致；不因短暂没有新起火误判结束；默认失败不再固定等待到 45 秒 | 中 |
| P0-2 | 让局部调整产生局部改善 | 先重新安排片区、传播入口和预算，构造可独立保护的住宅组；保留搬迁与建造 | 同一情景有至少三个合法参考布局产生不同保护数量，其中包含部分保护和达标；解释差异对应的布局改动 | 中至较大 |
| P0-3 | 让防火带与消防设施互有用处 | 用预算、保护范围和可见通道约束比较隔离与局部降温；审查全面封墙是否仍轻易解决全部问题 | 明确至少两种有取舍的可行方案：在不同已说明的空间约束下各有价值；检查最低成本明显解及混合设施 | 中，与 P0-2 联动 |
| P0-4 | 看懂并操作下一次调整 | 建造前显示占地、费用、覆盖和不可放原因；结算先给主要结果，再高亮一条与改动有关的传播证据；一键回到原布局 | 玩家能理解为何不能放置；结算无需读长日志即可找到损失位置；相同情景的前后对比正确 | 中 |
| P0-5 | 用真人反馈确认有效 | 开发完成后由用户先玩，再邀请 1–3 名首次玩家，无口头教学观察并复测 | 记录完整循环耗时、卡点、玩家对失败原因的解释及是否主动重试；至少完成一轮有真实来源的反馈与修复 | 需玩家参与 |

### P0-1 的结算边界

「没有火焰变化几秒」不能作为安全提前结算条件，因为热量可能继续累积。建议先实现确定可判定的情况：全部住宅失守，或玩家选择直接查看结果并在后台运行剩余固定步数。其余状态保留完整模拟上限；如另加稳定状态检测，必须证明剩余时间内不会再有住宅点燃。

界面区分「模拟时间」和实际观看时长；跳过演示不改变火势结果，不抹去可供复盘的事件。

### P0-2 / P0-3 的优先设计顺序

先检查地图空间与任务目标，再调整数值，最后才考虑新机制。建议尝试两个或三个住宅片区，让切断一条路径能保护一组住宅，避免单缺口必定损失全城。

如使用必须保留的通道，规则只要求该格不能布置防火设施，并提前标识；不引入居民或消防车寻路。地图大小、预算与住宅数量都可随验证调整，不为保留 v0.1 数值牺牲体验。

部分保护结果示例可以是保住 4、8、12 栋，但不预先宣称这些数值已能实现，也不要求所有局部改动都单调改善。有效策略必须来自模拟验证，不能只靠设计表描述。

### P0-4 的认知与因果边界

消防站当前提供提前降温，不能救回已燃烧住宅。建议先保留这种规则，将展示名称调整为「喷淋站（消防设施）」并清楚表现覆盖；这项命名待评估。直接加入主动灭火会改变平衡和操作节奏，暂不作为解决命名问题的首选。

复盘可表达「这里发生了绕行」「点燃时的主要相邻热源」，但不把当前单条 source 记录说成唯一历史原因。若要显示消防能力分摊或失效原因，需要先记录真实负载与热量证据。

## 4. P1：玩法通过后提升完成度

P1 不是不重要，而是依赖 P0 已验证的规则，避免反复返工。

| ID | 工作目标 | 建议范围 | 验收标准 | 新增成本 |
| --- | --- | --- | --- | --- |
| P1-1 | 形成短而完整的关卡节奏 | 复用街区表现，配置「局部隔离 → 通道与覆盖 → 风向迁移」三个不同问题；先两关，第三关可裁减 | 每关有学习目标、可复现参考布局；同一策略不能无修改包打全部关；切关不残留状态 | 中 |

| P1-5 | 提交环境可用 | 检查 Chrome / Edge、常见桌面尺寸、窄屏、失焦、刷新、无缓存加载与基础性能 | 明确测试设备与环境；无阻断错误；暂定目标是在选定参考设备上交互流畅且不持续低于 30 FPS，未测前不宣称达标 | 中 |

3D 表现以读图为先：保持建筑辨识、覆盖提示与坐标可见，修复遮挡和误点。暂不新增多层地图、自由镜头、真实倒塌物理或高成本资产。

## 5. 提交前必须完成的事项

这些是提交门槛，不能被 P1 / P2 的排序误解为可以省略。当前先准备；公开范围和实际部署仍按用户授权执行。

- 明确 GitHub 仓库的评审访问方式及公开范围。
- 启用 GitHub Pages 发布，获得实际可玩的 URL。
- 在无缓存浏览器通过正式 URL 完成首次进入、实验、调整、重试及最终流程；本地验证不能代替公网验收。
- README 提供游玩入口、操作说明、方向归属、AI 分工、真实迭代、用时边界、来源与未完成部分。
- 保留至少一次真实外部试玩及复测证据；没有发生的改进不补写成故事。
- 每个阶段将可接续版本和说明同步到 GitHub，继续支持多设备协作。

## 6. P2：当前暂缓，避免扩张

多种灾害、消防车和居民寻路、实时主动技能、经济系统、在线排行榜、账号、多人模式、无限随机地图、真实刚体破坏、复杂建筑升级树、高精度美术和为展示 3D 而加入的高度系统。

后续只有在试玩表明它能解决明确体验问题，并且核心目标已达成时，再重新评估。

版本名仅用于计划沟通，不是已经发布的版本。不要在 v0.2 前同时开做三个关卡和全部视听内容。

工时暂用相对新增成本表达，因为尚未确定截止时间和可参与试玩的人。后续每轮投入可参考实现 40%、试玩及修复 30%、内容配置 15%、文档 15%；实际用时独立记录。若时间收紧，先砍第三关、连续铺设和装饰效果，保留基础操作反馈、真人试玩与正式发布。

## 8. 用户评估时最关键的取舍

本计划的推荐默认值如下，均可在动手前调整：

1. 保持建造期决策为主，暂不加入火灾发生后的主动救火操作。
2. 先交付一个打磨过的实验，再扩展为 2–3 个短挑战；不将三关视为已批准的固定范围。
3. 继续保留住宅建造与搬迁；关卡用可见空间约束创造取舍，不指定唯一答案。
4. 喷淋站继续做提前降温，优先改名和反馈以匹配行为。
5. 达标后的优化以幸存数量和剩余预算分别展示，不急于合成总分或增加排行榜。

本轮仅整理目标和优先级供评估；实际实现规则仍以 `docs/07-rules.md` 为准。建议下一次实现范围只取 v0.2。
